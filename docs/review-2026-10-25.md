## What's in good shape

Worth saying first, because the rest of this doc is a defect list:

- **The core/plugin split is right.** `silt_core` is JUCE-free, so the engine is testable
  and the offline renderer/snapshot tools reuse it. That is what makes the UI work cheap.
- **The audio path is disciplined.** No allocation on the audio thread (`noteEvents`,
  `wet` preallocated), lock-free buffer swap with a message-thread free list
  (`Engine::collectGarbage`), `ScopedNoDenormals`, per-grain parameter latching, and a
  soft safety clip instead of a hard one.
- **State is versioned and self-describing** (`stateMagic`, `stateVersion`, XML + FLAC
  blob) and modulation routes are saved **by parameter id**, not by index — so routes
  survive a reordering of the parameter list. That is the single most important property
  for the mod feature to stay compatible, and it's already there.
- **The controller path is well thought out:** FIFO to the message thread, pickup to avoid
  jumps, learn that ignores repeat CCs, page-follows-controller. `TestController.cpp`
  covers the non-obvious parts.
- **Warning-clean** under `-Wall -Wextra -Wshadow` for everything in `core/` except one
  missing include (F3).

### F1 — Invisible, unclearable routes from the controller (high)

`slotParameter()` returns parameter ids for **menu and button slots**:

- menu slots the controller can reach (knob numbers are 1–8, as printed on the
  controller): `scale` (PITCH 2), `key` (PITCH 3), `endMode` (PLAY 5), `liveRun` (PLAY 5),
  `resNotes` (RESONATOR 2)
- button slots the controller can reach: `freeze` (PLAY 4), `resFollow` (RESONATOR 7)
- targets with **no editor control at all** (not in `slotParameter`, not a `Control`):
  `spaceMode`, `spaceFreeze`, `snap` — these can only have a route if it came from a saved
  state or a script

With ASSIGN on (or an armed modulator), `applyControllerMoves()` assigns a depth to *any*
modulation target:

```cpp
if (const int m = assigning.load(); m >= 0 && page != modPage && ! id.startsWith ("!"))
    if (const int t = modulationTarget (id); t >= 0)
        setRouteAmount (m, t, ...);          // PluginProcessor.cpp:1111
```

But the editor only wires depth gestures and the right-click "clear" menu onto **sliders**:

```cpp
for (auto& c : controls)
    if (c->menu == nullptr && c->button == nullptr)   // PluginEditor.cpp:748-751
        wireModulation (*c);
```

So a controller knob turned on the PITCH page (slot 2 = SCALE) can create a route that

1. is never drawn anywhere (no ring — there's no slider for it),
2. cannot be removed from the UI (no right-click target),
3. *is* saved with the project and keeps retuning grains.

That is the worst kind of bug for a user: a hidden state change with no undo path.

**Fix (pick two of three):**

1. **Restrict what can be a target** to continuous parameters (see F2). Removing choice and
   bool parameters from `targets[]` kills this class outright and is 3 lines.
2. **Give menus and buttons the same route management** as knobs — at minimum a route list
   (design doc §6), because even with (1) a future non-slider target would hit this again.
3. Belt and braces: in `applyControllerMoves`, only assign when the slot's control is a
   slider — but that duplicates UI knowledge in the processor, so I'd skip it if (1) lands.

A regression test is easy (`Rig` in `TestController.cpp`): turn knob 2 on PITCH with
`assigning` set, then assert `routeAmount(m, modulationTarget("scale")) == 0` if choices are
excluded — or assert the route is visible in `allRoutes()` if they're kept.

### F2 — No explicit modulation-target policy (medium)

Targets are "every parameter except a hardcoded list":

```cpp
const juce::StringArray fixed { "keyMode", "captureBars", "monitor", "sizeSync", "delaySync",
                                "spaceSync", "rateMode", "filterMode", "patternSeed" };   // :387
```

Everything else is a target, including:

| Kind | Examples | Ring display | Real effect |
|---|---|---|---|
| continuous float | `filterCutoff`, `pitch` | truthful | smooth |
| stepped int | `root`, `heads`, `grains`, `patternSteps` | suggests smooth | truncates to steps |
| choice | `scale`, `key`, `endMode`, `resNotes`, `liveRun`, `spaceMode`, `snap`, `sizeDiv`, `rateDiv`, `delayDiv`, `spaceDiv` | meaningless (0…1 of 12 items) | jumps between modes |
| bool | `freeze`, `resFollow`, `spaceFreeze` | none (button) | toggles at modulation rate |

The README ("Every parameter except mode switches, seeds and the modulators' own settings
can be modulated") doesn't match: `scale`, `key`, `endMode`, `resNotes`, `liveRun`,
`spaceMode` and `snap` are mode switches, and they *are* targets. Two of them
(`spaceMode`, `snap`) have no editor control at all, so the only place such a route can be
seen is a saved project.

Some of these are genuinely fun (an LFO on `heads`, a FOLLOW on `freeze`). My suggestion is
to make the policy explicit rather than delete it:

```cpp
enum class ModKind { continuous, stepped, switchLike };
ModKind modulationKind (const juce::RangedAudioParameter&);
```

- `continuous` → target, ring as today.
- `stepped` → target, but the ring draws to the *quantised* endpoints and the route list
  says "steps" (e.g. `+1.7 → +2 steps`).
- `switchLike` → **not** a target (keeps F1 from ever coming back), but still visible in the
  route list if a saved project contains one (forward/backward compatibility).

Deriving it from the parameter type (`AudioParameterFloat`/`Int`/`Choice`/`Bool`) is enough
and needs no per-id list.

### F3 — `SampleBuffer.h` is not portable (medium)

```
core/include/silt/SampleBuffer.h:19: error: 'size_t' was not declared in this scope
```

`SampleBuffer.h` includes only `<vector>` and uses unqualified `size_t`. libc++ (macOS) and
MSVC happen to leak `::size_t`; libstdc++ (Linux, some MinGW setups, many CI images) does
not. One-line fix:

```cpp
#include <cstddef>
```

Every other file in `core/` compiles clean. Because CI is macOS-only (F12), this stays
latent until someone tries a Linux build, which is a shame for a JUCE plugin (LV2/Linux is a
real target later).

### F4 — `maxTargets` can overflow silently in Release (medium, latent)

```cpp
jassert (targets.size() < (size_t) maxTargets);          // debug only
targets.push_back ({ ranged, params.getRawParameterValue (id) });
...
for (size_t t = 0; t < targets.size(); ++t)
    modulated[t].store (targets[t].raw->load());         // OOB write if over 160
```

Today there are **72 targets in the instrument build, 73 in Silt FX** (81 non-modulator
parameters per build, minus the fixed list, which includes `monitor` only on the instrument),
so there's plenty of headroom. But the mod work below will add parameters, and the failure mode is a
stack/buffer overrun in a release build. Two cheap options:

- Build `targets` first, then `assert` and clamp once; or
- Replace `std::array<std::atomic<float>, maxTargets>` with a vector sized in the
  constructor (routes as `std::vector<std::atomic<float>>` of `numModulators * n`).

Add a unit test that just checks `numTargets() < maxTargets` so CI fails loudly before it
becomes an overrun.

### F5 — `static` scratch buffer in `timerCallback` (medium, latent)

```cpp
static std::array<silt::GrainView, SiltProcessor::maxGrainViews> views;   // :1072
const int n = silt.readGrainViews (views);
```

Function-local statics are per *process*, not per editor. Two Silt windows open (two tracks,
or two instances in the same process) share this buffer, so two message-thread timers can
interleave writes/reads while `readGrainViews` retries on its sequence counter. In practice
the window is tiny, but it's a data race with a trivially cheap fix: make it a member
(`std::array<silt::GrainView, SiltProcessor::maxGrainViews> viewsScratch;`). It also moves
24 KB of hot state out of `.bss`.

### F6 / F7 — Small editor hazards

**F6:** `PluginEditor.h:116`

```cpp
float param (const char* id) const { return silt.params.getRawParameterValue (id)->load(); }
```

Any typo in the ~30 call sites (`param("freeze")`, `param("snap")`, …) is a null
dereference in Release. Make it defensive:

```cpp
float param (const char* id) const
{
    const auto* p = silt.params.getRawParameterValue (id);
    jassert (p != nullptr);          // catches typos in debug
    return p != nullptr ? p->load() : 0.0f;
}
```

Same pattern in `SiltProcessor::slotParameter`'s `v()` lambda (`:993`).

**F7:** `PluginEditor.cpp:708` and 10 neighbours:

```cpp
addKnob (Page::mod, 2, id ("Shape").toRawUTF8(), "SHAPE")
```

`id()` returns a temporary `juce::String`; `toRawUTF8()` points into it. It's valid for the
whole full-expression, and `addKnob` uses it immediately (component id + `SliderAttachment`),
so it's correct **today**. But it is one refactor away from a dangling read. Change
`addKnob`/`addButton` to take `const juce::String&` and pass `id ("Shape")`.

### F8 — The mod palette exists twice and has drifted (low, but visible)

`drawModulation` (`:949`):

```cpp
rust            0xffa64826
gold            0xffd29a2c
green           0xff6f8f4e
blue            0xff4f62a8
```

Header stripes (`:1276`):

```cpp
rust            0xffa64826
gold            0xffd9a03a      // ≠ d29a2c
green           0xff8fa27a      // ≠ 6f8f4e
bone            0xffefe6cf      // ≠ 4f62a8 — not even the same hue
```

So the "four stripes" motif in the header, which reads as "four of something", doesn't
correspond to the four modulators, and three of the four colours are near-but-not-equal
duplicates. One `ModColours.h` fixes both (design doc §5).

### F9 — Ring/dot geometry mismatch

Arcs at `radius + 3.0f * ring`, dot at
`radius + 1.5f + 3.0f * (ring - 1) * 0.5f`. For one route the dot sits at `radius + 1.5`
while the arc is at `radius + 3`; for two routes the arcs are at +3/+6 and the dot at +3.0
(on top of the first arc). It reads as "the dot is on the innermost ring" only by accident.
Compute both from one function: `ringRadius (i) = radius + 3.0f * (i + 1)`, dot on
`ringRadius (ring - 1)`.

### F10 — Armed modulator survives the editor

`assigning` lives in the processor (right, the controller needs it), but closing the window
while ASSIGN is on leaves the controller in depth-editing mode with nothing on screen
saying so. Either clear it in `~SiltEditor()`, or make it visible on every page — which is
what the design doc's mod chips do anyway.

### F11 — Layout is fixed and the tab row is full

`editorWidth = 1040`, `editorHeight = 600`, no `setResizable`, no scale persistence. The
nine tabs are `110` px each = 990 px of a ~1008 px interior: **one more page overflows**.
Any new page (or an "ADVANCED" tab) has to share space. Options, cheapest first:

1. `tab.setBounds (tabs.removeFromLeft (tabs.getWidth() / numPages) ...)` so tabs fit any
   width, then `setResizable (true, true)` with `setResizeLimits (860, 520, 1600, 1000)` and
   a `resized()` that is already coordinate-relative (it mostly is — only font sizes and the
   screen's fixed 272 px are absolute).
2. Persist the window size in the state tree (`editorWidth`/`editorHeight` properties).
3. Only then consider a tenth page.

### F12 — README/CI drift

`README.md` says CI "builds on macOS and Windows and runs pluginval on both VST3 builds";
`build.yml` has `os: [macos-14]` with a comment that `windows-2022` "returns once the
Windows build is fixed". Worth aligning the README, and worth reconsidering a cheap
**ubuntu-latest** job that only builds `silt_core` + `silt_tests` (no JUCE) — that would
have caught F3 in a minute of CI time.

### F13 — ENVELOPE mod can stick in sustain

`modContext.heldNotes` is a plain counter incremented on every note-on and decremented on
every note-off (`:767`, `:770`). A duplicate note-on for a note that is already held (some
controllers/arps do this, and hosts can send it on clip retrigger) followed by one note-off
leaves the count at 1, so `Modulator::envelope` never enters release and the ENVELOPE mod
holds sustain forever — until an All Notes Off arrives.

Cheap fix: keep a 128-bit (or `std::array<bool,128>`) held-note set in the processor and
derive the count; it's a per-event O(1) update and removes the whole class of mismatch.
`allNotesOff` already resets it (`:731`), which is why this is rare but real.

### F14 — `modOutputs` is dead

Written every chunk (`:862`), read nowhere. That's exactly the data a modulator meter wants
— see design doc §3/§4. Either surface it or drop it; today it's 16 bytes of write traffic
and a misleading public API.

## Test gaps

The DSP and controller tests are good. What isn't covered, and what I'd add before touching
the mod UI:

1. **Editor layout ↔ `slotParameter` agreement.** The page/slot map is written twice — once
   as `addKnob(Page::filter, 1, "filterCutoff", …)` and once as
   `case 5: { const char* ids[] { "filterMode", "filterCutoff", … } }` — with nothing tying
   them together. Move one control and the controller silently drives the neighbour.
   `silt_plugin_tests` already compiles the editor, and `silt_snapshot` already builds an
   editor headlessly, so a test can do this without a display:

   ```cpp
   // for each page: show it, then for every visible slot check
   // editor.visibleParameterId (page, slot) == processor.slotParameter (page, slot)
   ```

   That needs one small accessor on the editor. It is the highest-value test in this repo
   for future UI work.
2. **Route policy:** that a choice/bool parameter is not a target (F2), and that no route
   can exist that isn't listed by the route enumeration (F1).
3. **Mute/clear-all** (once it exists): muted modulator contributes 0, cleared modulator
   leaves base values, and both round-trip through state.
4. `numTargets() < maxTargets` (F4).
5. A `silt_snapshot` PNG per page after the mod redesign, so the visual diff is reviewable
   in PRs (the tool already exists; it just needs the new pages listed).

## Structure suggestions (non-urgent, but they pay off)

`plugin/PluginEditor.cpp` is 1,321 lines holding the palette, `PanelLook`, `GrainScreen`,
the page table, the mod wiring and the paint code. Splitting it mechanically — no behaviour
change — makes the mod work much easier:

```
plugin/PanelLook.h/.cpp      look & feel + palette tokens (chosen once)
plugin/ModColours.h          the four source colours (§5 of the design doc)
plugin/GrainScreen.h/.cpp    the screen
plugin/PageLayout.h          page/slot/param table, shared by editor + controller
plugin/ModPanel.h/.cpp       chips + focused editor + route list (new)
plugin/PluginEditor.cpp      assembly, strip, tabs
```

The `PageLayout` table is the one with real value: a single `{ page, slot, paramId,
alternative condition, controlKind }` list consumed by *both* the editor (to build controls)
and `SiltProcessor::slotParameter` (to answer the controller). Today the two are duplicated
by hand and only agree because someone checked. A shared table + test #1 above removes a
whole category of future bug, and it's the natural place to hang the new MOD page.

One naming note while you're in there: `assigning` is really "the armed modulator". Renaming
it `armedMod` (−1 = none) makes the advanced-mode code read correctly, and
`clearRoutes(target)` → `clearRoutesOnTarget(target)` next to a new
`clearRoutesForModulator(m)` removes the ambiguity that makes "remove a mod source" hard to
talk about (see design doc §6).
